# Document Search

Простой асинхронный поисковик по текстам документов: **FastAPI**, документы хранятся в **PostgreSQL**, полнотекстовый индекс — в **Elasticsearch**.

| Метод | Путь | Что делает |
|---|---|---|
| `GET` | `/api/v1/documents/search?query=…` | ищет запрос по тексту в индексе и возвращает 20 самых релевантных документов со всеми полями из БД, упорядоченных по дате создания |
| `DELETE` | `/api/v1/documents/{id}` | удаляет документ из БД и из индекса |
| `GET` | `/api/v1/documents/{id}` | возвращает документ (вспомогательный метод) |
| `GET` | `/health` | проверяет доступность PostgreSQL и Elasticsearch |

Документация API в формате OpenAPI 3.1 — [`docs.json`](docs.json); Swagger UI поднятого сервиса — http://localhost:8000/docs.

## Стек

- Python 3.12, FastAPI, Uvicorn;
- PostgreSQL 16, SQLAlchemy 2.0 (asyncio) + asyncpg;
- Elasticsearch 8.15 и официальный асинхронный клиент `AsyncElasticsearch`;
- httpx — асинхронное скачивание датасета и HTTP-клиент в тестах; pytest + pytest-asyncio;
- Docker и Docker Compose.

Все обращения к PostgreSQL, Elasticsearch и сети асинхронные.

## Быстрый старт

Нужны Docker с Compose v2 и примерно 2 ГБ свободной памяти (из них 512 МБ — heap Elasticsearch).

```bash
make up     # собрать образ из исходников и запустить PostgreSQL, Elasticsearch и API на http://localhost:8000
make load   # скачать датасет и загрузить его в PostgreSQL и Elasticsearch
```

### Датасет

`make load` сам скачивает CSV с Яндекс Диска через публичное REST API и сохраняет его в `data/posts.csv`. Если скачать не получилось (например, у контейнера нет доступа в интернет), скачайте файл [по ссылке](https://disk.yandex.ru/d/UYooXd9q2yqTMQ) вручную, положите его в `data/posts.csv` и повторите `make load`.

Проверяем:

```bash
curl -sG http://localhost:8000/api/v1/documents/search --data-urlencode 'query=отличная погода'
curl -i -X DELETE http://localhost:8000/api/v1/documents/1
```

Все команды — `make help`. Без `make` те же действия выполняются напрямую:

|---|---|
| `make up` | `docker compose up -d --build` |
| `make load` | `docker compose run --rm loader --download` |
| `make reload` | `docker compose run --rm loader --download --recreate` |
| `make reindex` | `docker compose run --rm loader --reindex` |

## API

### Поиск

`GET /api/v1/documents/search`

| Параметр | Обязательный | Описание |
|---|---|---|
| `query` | да | произвольный текст, от 1 до 1000 символов, не из одних пробелов |
| `order` | нет | `desc` (по умолчанию, сначала новые) или `asc` (сначала старые) |

Ответ `200`:

```json
{
  "total": 137,
  "items": [
    {
      "id": 42,
      "rubrics": ["VK-1603736028819866", "VK-47360980"],
      "text": "Сегодня отличная погода для прогулки",
      "created_date": "2019-11-25T12:34:42"
    }
  ]
}
```

`total` — сколько документов в индексе соответствует запросу, `items` — не более 20 документов. Ошибки: `422` — некорректные параметры, `503` — PostgreSQL или Elasticsearch недоступен.

### Удаление

`DELETE /api/v1/documents/{id}` → `204` — документ удалён из БД и из индекса; `404` — такого документа нет; `422` — некорректный `id`; `503` — PostgreSQL или Elasticsearch недоступен, ничего не удалено.

## Как это устроено

**Хранилище.** PostgreSQL — источник истины: таблица `documents (id serial, rubrics text[], text text, created_date timestamp)` с индексом по `created_date`. Индекс Elasticsearch `documents` содержит только `id` и `text`, `_id` документа в индексе равен `id` в базе. Таблица и индекс создаются при старте приложения, если их ещё нет.

**Поиск.** Запрос выполняется как `match` по полю `text` с встроенным анализатором `russian` (приведение к нижнему регистру, стоп-слова, стемминг: запрос «машины» находит «купили машину»). Elasticsearch возвращает `id` 20 самых релевантных документов, затем одним запросом `SELECT … WHERE id IN (…) ORDER BY created_date` из PostgreSQL берутся документы со всеми полями. Сортировка выполняется в базе, потому что по условию задания в индексе нет даты.

**Удаление.** Строка удаляется в транзакции, которая фиксируется только после удаления документа из индекса. Если Elasticsearch недоступен, транзакция откатывается и сервис отвечает `503`: документ остаётся и в базе, и в индексе, хранилища не расходятся. Удаление из индекса выполняется с `refresh=wait_for`, поэтому после ответа `204` документ гарантированно не попадёт в выдачу. Цена — DELETE отвечает до секунды (интервал обновления индекса), и всё это время строка в PostgreSQL заблокирована. Для сервиса, где удаления редки, это осознанный компромисс; при массовых удалениях от `wait_for` можно отказаться, а удалённые, но ещё видимые в индексе документы и так отсеются, потому что поля берутся из базы.

**Недоступность хранилищ.** Если не отвечает PostgreSQL или Elasticsearch, API возвращает `503` с описанием в `detail`, а не `500`. Ошибки базы, которые означают баг в запросе, а не сбой, по-прежнему дают `500`. Клиент Elasticsearch делает не больше одного повтора, поэтому при упавшем кластере запрос завершается за секунды.

**Загрузка датасета** (`python -m app.loader`). CSV читается потоково, документы вставляются в PostgreSQL пачками по 500, после чего индекс строится из базы через bulk API, поэтому `id` в индексе всегда совпадают с `id` в базе. Некорректные строки (без даты, с пустым текстом или с битым списком рубрик) пропускаются с предупреждением в логе; пустые элементы списка рубрик (`None`, `null`, `''`) отбрасываются. Повторная загрузка без `--recreate` отклоняется, чтобы не задвоить документы. `--reindex` пересобирает индекс по данным из базы.

## Тесты

```bash
make test
```

Тесты запускаются в отдельном контейнере против настоящих PostgreSQL и Elasticsearch из `docker-compose.yml`, но работают с отдельной базой `search_test` и индексом `documents_test`, поэтому загруженные данные не затрагиваются. Перед каждым тестом база и индекс очищаются. Запросы идут через HTTP-клиент httpx прямо в ASGI-приложение.

Что проверяется:

- поиск: в ответе все поля из БД; сортировка по дате в обе стороны; не больше 20 результатов, причём отбираются самые релевантные (более новые, но менее релевантные документы их не вытесняют); русская морфология; пустой результат; валидация параметров; `503`, если недоступен PostgreSQL или Elasticsearch;
- получение и удаление: документ пропадает и из БД, и из индекса, а остальные остаются; `404` и `422`; откат удаления, если Elasticsearch недоступен; `503` без изменений в хранилищах, если недоступен PostgreSQL;
- `/health`: `200`, когда всё доступно, и `503` с указанием, какое хранилище не отвечает;
- какие ошибки базы считаются недоступностью (`503`), а какие остаются багом (`500`);
- загрузка датасета: разбор CSV (многострочные тексты, рубрики, даты, пустые тексты, битые строки), заполнение БД и индекса, защита от повторной загрузки;
- `docs.json` описывает те же эндпоинты, параметры и коды ответов, что и приложение.

Проверка поднятого сервиса «чёрным ящиком» на реальном датасете (только стандартная библиотека Python; удаляет один документ):

```bash
python scripts/check_service.py                      # или: --base-url http://host:8000 --csv path/to/posts.csv
```

## docs.json

Спецификация OpenAPI 3.1 лежит в корне репозитория, и сервис отдаёт её же по адресу `/docs.json` (Swagger UI — `/docs`, ReDoc — `/redoc`). После изменения API спецификацию можно перегенерировать из кода командой `make openapi`, а тест `tests/test_openapi.py` не даст ей разойтись с приложением.

## Конфигурация

Настройки берутся из переменных окружения (или из файла `.env`); в Docker Compose они уже заданы.

| Переменная | По умолчанию | Описание |
|---|---|---|
| `POSTGRES_HOST` | `localhost` | хост PostgreSQL |
| `POSTGRES_PORT` | `5432` | порт PostgreSQL |
| `POSTGRES_USER` | `postgres` | пользователь |
| `POSTGRES_PASSWORD` | `postgres` | пароль |
| `POSTGRES_DB` | `search` | база данных |
| `ELASTICSEARCH_URL` | `http://localhost:9200` | адрес Elasticsearch |
| `ELASTICSEARCH_INDEX` | `documents` | имя индекса |
| `SEARCH_LIMIT` | `20` | сколько документов возвращает поиск |
| `TEST_POSTGRES_DB` | `search_test` | база для тестов |
| `TEST_ELASTICSEARCH_INDEX` | `documents_test` | индекс для тестов |

Сервис в контейнере работает от непривилегированного пользователя, у `db`, `elasticsearch` и `app` задано `restart: unless-stopped`. Загрузчик запускается от root: он пишет датасет в примонтированную папку `data/`, владелец которой на хосте заранее неизвестен.

Порты PostgreSQL и Elasticsearch наружу не публикуются, чтобы не конфликтовать с локально установленными сервисами. Заглянуть в индекс можно так: `docker compose exec elasticsearch curl -s localhost:9200/documents/_count`.

## Запуск без Docker

Понадобятся Python 3.12 и доступные PostgreSQL и Elasticsearch 8.x.

```bash
python3.12 -m venv .venv && source .venv/bin/activate
pip install -r requirements-dev.txt
export POSTGRES_HOST=localhost ELASTICSEARCH_URL=http://localhost:9200   # и остальные переменные при необходимости
python -m app.loader --download          # загрузка датасета
uvicorn app.main:app --reload            # сервис на http://localhost:8000
pytest                                   # тесты создадут базу search_test сами
```

## Допущения

- «Первые 20 документов, упорядоченные по дате создания» понимаются так: 20 самых релевантных совпадений, отсортированные по `created_date`. По умолчанию сначала идут новые, `order=asc` меняет порядок.
- В CSV нет `id`, поэтому его присваивает PostgreSQL при загрузке.
- `created_date` хранится как `timestamp without time zone`, как в исходных данных; даты с часовым поясом при загрузке приводятся к UTC.
- `id` хранится как `INTEGER` (int4), поэтому API принимает id от 1 до 2 147 483 647; остальные значения отклоняются с 422.
- При удалении документ сначала удаляется из индекса, затем фиксируется транзакция в PostgreSQL. Если Elasticsearch недоступен, транзакция откатывается и обе системы остаются без изменений (503). Если же упадёт сам коммит в PostgreSQL (крайне редкий случай), документ останется в базе, но исчезнет из индекса; согласованность восстанавливает `make reindex`.
- Схема из одной таблицы создаётся при старте через `create_all`, миграции (Alembic) для задания такого размера не заводились.
- `make reindex` удаляет индекс и строит его заново, поэтому на время пересборки поиск отвечает `503` или неполными результатами. Без простоя пересборка делается через новый индекс и атомарное переключение alias; для тестового задания это избыточно.
- Образ сервиса всегда собирается локально из исходников (`search-service:local`), чтобы запускался ровно тот код, что в репозитории. В реальном проекте образ собирал бы CI, тегировал git SHA и версией релиза, а деплой шёл бы по неизменяемому тегу или digest.
